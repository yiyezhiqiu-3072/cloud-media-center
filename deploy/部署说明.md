## 三、部署步骤

### 1. 备份现有部署目录
把目前服务器上正在运行的 4 个目录（例如 `C:\Cloud\CloudMusic\dist\` 等）整个复制一份留底，
尤其是里面的 **`data\` 文件夹**（曲目、上传的音乐、工作日志数据全在里面）。

### 2. 替换 exe
把本包 4 个目录里的 `.exe` 分别覆盖到对应部署目录。

⚠️ **不要覆盖你现在正在用的 `config.json`**。本包里的 `config.json` 只是「新装一份」的参考模板，
端口/账号按 nginx 标准写好了。如果你现有配置里改过 `data_dir`、账号密码或端口，
请**保留原文件**，只替换 exe 和新增 ffmpeg.exe。

### 3. 放置 ffmpeg（关键一步）
把 `CloudMusic/ffmpeg.exe` 复制到 **`CloudMusic.exe` 所在的同一个文件夹**。
例如 exe 在 `C:\Cloud\CloudMusic\dist\`，就放到 `C:\Cloud\CloudMusic\dist\ffmpeg.exe`。

程序会按以下顺序自动查找，**放在 exe 同级即可零配置生效**：

1. `config.json` 里的 `ffmpeg_path`（可填绝对路径或相对 exe 目录的路径）
2. `<exe 同级>/ffmpeg.exe`
3. `<exe 同级>/ffmpeg/ffmpeg.exe`
4. `<data 目录>/ffmpeg.exe`、`<data 目录>/ffmpeg/ffmpeg.exe`
5. 系统 PATH 里的 `ffmpeg`

如果希望放到别处，就在 `config.json` 里写绝对路径，例如：

```json
"ffmpeg_path": "D:\\ProgramData\\WorkBuddy\\ffmpeg\\ffmpeg.exe"
```

### 4. 启动
按原有顺序启动即可（CloudAuth 先起，再起其余 4 个）。启动日志会打印：

```
ffmpeg：C:\...\ffmpeg.exe
服务端自动转码：已启用
```

若显示「未找到」，说明第 3 步位置不对，按上面的查找顺序检查。

### 5. 重启后硬刷新浏览器
桌面端与手机端都按 `Ctrl+F5`（手机用无痕窗口或清缓存）刷新一次，
确保加载最新的共享播放条脚本。

## 四、转码功能说明

### 做什么
上传的 **wav / flac / aiff / caf / mp4（音频）** 会在服务端后台自动转成通用 mp3，
播放时优先用转码结果（`audio/mpeg`），彻底绕开浏览器对这些格式解码能力的差异。
mp3 / m4a / aac / ogg / opus / webm 浏览器原生支持，保持原文件直出，不浪费时间和磁盘。

### 关键行为
- **不阻塞上传**：上传请求先返回，转码在后台线程进行。
- **不阻塞播放**：播放时只用「已生成好的缓存」；还没转好就先直出原文件并异步补转。
- **原文件永不改动**，转码缓存单独放在 `data/transcodes/<曲目ID>_auto.mp3`。
- **历史曲目自动补转**：程序启动后会后台串行检查并补转以前上传的文件，不用重新上传。
- **删除曲目会自动清理**对应的转码缓存。
- **没装 ffmpeg 也不会出错**：自动回退原文件 + 按扩展名规范化的 Content-Type（上一版已修复 wav 的 MIME 问题）。
- **码率切换**（播放页里选 64/96/128/192/256/320 kbps）现在也会因 ffmpeg 到位而启用。

### 配置项（CloudMusic 的 config.json，改完自动热重载，无需重启）
```json
"auto_transcode": true,          // 总开关，false 则完全直出原文件
"auto_transcode_kbps": 192,      // 目标码率，范围 64~320
"ffmpeg_path": ""                // 留空 = 自动发现；也可写绝对路径
```

> 改 `auto_transcode_kbps` 不会重建已有缓存；想用新码率需删除 `data/transcodes/` 下的 `_auto.mp3`。

## 六、常见问题

**Q：转码很慢 / CPU 占用高？**
历史曲目是**后台串行**逐个转的，只跑一个 ffmpeg 进程，不会打满 CPU；期间服务与播放都正常。
首次部署时曲目多会持续一段时间，看 `transcode_pending` 降到 0 即完成。

**Q：磁盘会涨多少？**
每首需转码的曲目多存一份 192kbps mp3（约每分钟 1.4MB）。原文件保留，
如需省空间可关闭 `auto_transcode` 并删除 `data/transcodes/`（会回退到上一版 MIME 规范化方案）。

**Q：某首 wav 仍报播放器错误？**
看日志是否有「服务端转码失败」。多为源文件本身损坏或编码异常；
可把该文件名发来排查。转码缓存生成前的首播会直出原文件，稍等片刻再点即可。

**Q：只想更新前端、不想换 exe？**
不行——本次转码改的是后端 Python 逻辑，**必须替换 `CloudMusic.exe`**。
但「桌面端统一成一条播放条」是纯前端改动，可用热更新：把 `player.js` 覆盖到
各应用 exe 旁的 `static/` 目录即可。本包已把 4 个 exe 全部同步重打，直接整套替换最省事。

### 改了什么
共享播放条由一行改为**两行**：上排仍是封面 / 歌名 / 状态 / 播放控制，
**下排新增「已播放时间 + 圆角进度条 + 剩余时间」**：

## 十二、甘特图切换真因修正（v1.1.4）

**发版时间：2026-11-08 11:08:59** ｜ CloudWork `1.1.3` → **`1.1.4`**（本次只重打 CloudWork.exe，
其余 3 个 exe 不涉及；点版本号可看本次内容与历史）

上一节说「自动定位」但实际没生效，真正的根因在这里：
`#recordView` 带 `.layout { display: grid }`，**作者样式会覆盖浏览器默认的 `[hidden]{display:none}`**，
所以点「查看甘特图」时记录页**从未隐藏**，甘特图一直被挤在它下方；
自动滚回顶部反而让用户又看到表单，看起来像「点了没跳过去」。

修复：
- 样式表加全局 `[hidden] { display: none !important; }`；
- `setView()` 里再用 inline `style.display` 做双保险（不依赖样式表优先级）；
- 配合上一节的 `scrollTo(0)`，切换后才会真正把整个甘特图显示在首屏。

自检：点「查看甘特图 →」，页面应**只剩甘特图**（记录表单消失）并停在甘特图顶部；
点「← 返回记录」表单恢复、甘特图消失。
